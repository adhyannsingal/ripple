# ADR 0033 — Cooperative cancellation and explicit index retention

Status: accepted; implemented and verified in M9-T04.

The CLI installs a per-command control context: 120 seconds by default, configurable with --timeout-seconds (1..86400), and a Ctrl-C/SIGTERM cancellation flag. Library calls have no command-wide deadline unless a caller installs a context; existing subsystem budgets still apply. Open Store inside that scope so SQLite callbacks bind its control token. Main-thread analysis/capture/traversal checkpoints and Tree-sitter/SQLite progress callbacks observe it. A running trusted Git direct child is killed and waited on before cancellation returns. This is cooperative cancellation, not hard real-time preemption or an OS process-memory limit; individual filesystem/system calls, sorting/serialization and commit/checkpoint operations can delay observation. Arbitrary descendants of malicious executables are outside the trusted-Git model.

Cancellation before a generation's final commit check rolls back the transaction; prior complete generations remain usable. A signal arriving during/after COMMIT cannot revoke that commit. The command reports committed state and any pending derived-file work rather than claiming rollback. Read commands check cancellation before emitting a success report. Ctrl-C cannot silently publish partial analysis.

Default persistent limits are 1024 MiB of live SQLite generation payload, a 1024 MiB SQLite page budget, and 256 retained generations. Index flags may set --max-index-mib and --max-generations. Existing oversized stores remain readable and may be explicitly pruned; another publication is rejected with instructions. Limits count stored input bytes and serialized facts/evidence, not just sources. SQLite page limits and transaction rollback provide an additional storage bound. WAL/journal/temporary files, allocation overhead and derived caches mean these limits are not a hard filesystem quota; transient operations can use more space.

There is no automatic expiry or deletion. `ripple index . --prune-to N` is an explicit maintenance-only action retaining the active generation and newest older generations, never rebuilding or publishing a new generation. Only removed generations' derived modules-N.json files are eligible for cleanup; later explicit pruning also retries canonical numeric orphan names older than the active generation and absent from the retained set. Noncanonical, future and unrelated names are preserved. Unknown files, user sources, Git state and active generation artifacts are never removed. Deletions occur transactionally under the writer slot; cancellation/quota failures before COMMIT leave retained data unchanged. Old open reader transactions retain their consistent SQLite snapshot.

Pruning returns reusable database pages; SQLite need not shrink the file. Optional --compact with --prune-to requests SQLite VACUUM and WAL truncation, which may need substantial temporary disk space and may be blocked by other readers. Compaction/file cleanup failures after prune commit are reported as pending, not falsely described as a rolled-back prune. No migration, format-v1/schema-v2 change or unsupported-semantics expansion is introduced.

Signal handling uses pinned [ctrlc 3.5.2](https://docs.rs/ctrlc/3.5.2/ctrlc/); SQLite progress hooks and page limits use the existing pinned rusqlite/SQLite backend. Authored Rust remains unsafe-free. Native SIGINT/SIGTERM child-reaping tests run on Unix; Native Windows console-event injection remains unmeasured; portable control/SQLite/quota/CLI tests passed Windows CI.
