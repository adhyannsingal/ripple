# Performance evidence

[Verified workflow report](../bench/results/workflows/README.md) records actual CLI cold throughput, no-op/body incremental p50/p95, verified impact p50/p99, startup proxy, storage/capture/module/adjacency/traversal stages, impact peak RSS and three-generation index size. Workload/source/binary/helper hashes, machine/toolchain/state, nearest-rank statistics and raw samples are linked there. The older [M6 update report](../bench/results/README.md) covers two finite library workloads and excludes real Git provenance; it is a different measurement boundary.

The 65-file supported chain is deliberately small/synthetic (65 one-line LOC); no general throughput or latency promise follows. OS caches are warm, application indexes are fresh per sample and updates have known prior state. End-to-end values include real Git and serialization; pure traversal/cached storage do not verify live content. Startup is measured separately with --version, never subtracted to invent exact traversal time. No shared-CI absolute threshold.

The phase profile identifies capture/verification as dominant (~300 ms p50), versus storage ~3.3 ms and pure traversal ~1.6 ms. A metadata-only cached-freshness shortcut was rejected: a same-size body edit with restored mtime looks unchanged to that shortcut while production correctly reports stale state. No unsafe shortcut was shipped and no unmeasured before/after gain is claimed. See the report's counterexample and raw evidence. Larger repositories, kernel-cold runs, long archive growth and peak cold-index RSS remain unmeasured. Candidate source/version changes require a final rerun before release readiness.
